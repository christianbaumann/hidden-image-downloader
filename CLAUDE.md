# Project: Hidden Image Downloader

A Chrome extension that downloads images which JoyClub hides behind a transparent GIF (or similar overlay), so the browser's own "Save image" grabs the overlay instead of the image.

## Stack
- **Language:** Vanilla JavaScript (no frameworks)
- **Targets:** Chrome, Manifest V3, JoyClub only. Firefox is not supported yet (see below).

## Conventions
- No build step, no transpilation. Plain `.js` files loaded directly by the extension.
- Runtime dependencies are vendored in `vendor/` — not via npm.
- Dev tooling (ESLint, Playwright, …) lives in `package.json` devDependencies — npm is fine for tools that never ship in the extension.
- Firefox: MV3 needs `browser_specific_settings.gecko` (`id`, `data_collection_permissions`) and `background.scripts` instead of `background.service_worker`. Not handled yet; `web-ext lint` reports it.
- Extension code is ES modules: `background.js` is a module service worker importing `lib/*.js`. Exception: `content.js` (content scripts cannot be modules). `eslint.config.js` lints root `*.js` and `lib/**/*.js` as modules with browser + `chrome` globals.
- Chrome ignores the `filename` passed to `chrome.downloads.download()` while any other extension listens to `downloads.onDeterminingFilename` (e.g. MarkSnip, Video DownloadHelper). `background.js` therefore suggests its own filename in that event, only for downloads it started.
- Functions injected via `chrome.scripting.executeScript({ func })` are serialised: keep them self-contained (no imports, no closures). Put parsing into pure `lib/` functions.
- Lightbox and menu images: `firstAvailable` in `background.js` probes each candidate of `imageCandidates` but the last with `HEAD` (5 s timeout each): the full-size jpg (`toFullSizeUrl`; none for full-size, gated or `pxl_` images), the `.jpg` sibling of a `.webp`, then falls back to the URL as served. In production the probe goes to a host-permitted origin; in E2E it goes to `127.0.0.1`, which has no host permission, so the fixture server must send credentialed CORS headers (`Access-Control-Allow-Origin: <Origin>`, `Access-Control-Allow-Credentials: true`).
- Single-image filename (lightbox and context menu): `buildFilename` in `lib/filename.js` → `<Owner>_<Album>_<nn>_<photo-id>.<ext>` when album title and a 1-based position within `count` are known, else `<Owner>_<photo-id>.<ext>`; no timestamp. It shares `photoStem` with the ZIP entries (`albumEntries`, numbered by position in `userImageIdList`, so a photo without source leaves a gap), so a photo gets the same name both ways (except a `-2` folder suffix, which only the ZIP knows). `<photo-id>` is `photoKey(url)` (first 8 chars of the UUID path segment), else `data-photo`, else `image`; jpg and `.webp` fallback share one stem. `extractLightboxData` reads no album context yet: no live selector is known (`.agents/changes/2026-10-09-missing-features/research-04-lightbox-context.md`).
- Context menu "Save hidden image" (`contextMenus`, created in `runtime.onInstalled`, every page context but not `'all'`, which would add it to the toolbar icon's menu too, `documentUrlPatterns` JoyClub): `content.js` (manifest `content_scripts`, JoyClub only, `run_at: document_start`, `all_frames: true`, since `documentUrlPatterns` also shows the menu in JoyClub iframes; a classic script, so no imports, and its `DESCRIBE_ACTION` string is repeated in `background.js`) stores the last `contextmenu` position. `handleMenuClick(info, tab)` asks it via `tabs.sendMessage(…, { frameId: info.frameId })`; it answers with `elementsFromPoint` layers without `body`/`html`, each preceded by its descendants under the point that `elementsFromPoint` skips (JoyClub's lightbox `.secure_image` has `pointer-events: none`) (computed `backgroundImage`, `backgroundColor`, `srcset` incl. `<picture>` sources, an `img`'s own `src`, `data-photo`, index of the closest `a.album-link`, lightbox `a.lb_owner_name`, closest `[user-name]` (feed `j-member-card`)) plus page owner (`h1.profile-base-info__user-name`), album (last `h2.profile-headline` before the first `a.album-link`; the own profile has an earlier "Account" headline in `.profile-membership-and-coins-info`) and `a.album-link` hrefs. An exception while describing answers `null` ("image address not found"). `toHiddenImageCandidates` (`lib/hidden-image.js`, pure) takes the first layer with a background image, else the widest srcset entry, else a non-GIF http(s) `src` (`plainImageUrl`; overlays are data-URI or `.gif` GIFs); owner = lightbox owner, else card `user-name`, else page owner; but stops at a backdrop (a layer without image whose background colour has alpha ≥ `BACKDROP_MIN_ALPHA` 0.6, e.g. beside the lightbox photo; a hover tint stays below that), and adds album/position/count only on `/profile/fotoalbum/…` (own link index, else the lightbox's `data-photo` in `#media_id_0_<id>_`); then `imageCandidates` (`lib/lightbox.js`, shared with the toolbar lightbox: full-size jpg via `toFullSizeUrl` (`/<uuid>/<variant>/image_<w>_<token>.<ext>` → `/<uuid>/orig/image_1920_<token>.jpg`, verified live for `1-1` crops and `orig/image_180`), then the jpg sibling, then the URL as served; a layer inside an `a[href*="/webauth/activate/fsk18/"]` link is `gated` (served only as `image_180_pxl_…`) and throws `Fsk18LockedError`, see FSK18 unlock) → `firstAvailable` → `startDownload`. No answer from the content script (tab opened before install/reload) → `PageNotReadyError` ("reload the page and try again"); no image layer → `NoImageUrlError`. Both use the shared `reportFailure` (red badge + log). The page owner selector works on album pages (verified live). E2E dispatches a `contextmenu` event in the page and calls `globalThis.handleMenuClick` in the service worker.
- Profile ZIP: `background.js` opens `offscreen.html` (reason `BLOBS`); `offscreen.js` fetches the photos, zips them with `lib/zip.js` and answers with a blob URL. The service worker downloads that URL via `chrome.downloads` (filename enforced in `onDeterminingFilename`) and closes the document once every ZIP download is `complete` or `interrupted`, since the blob URL dies with the document. Resuming an interrupted ZIP download therefore fails. ZIP names carry no timestamp (`<Owner>.zip`, `<Partner>_ClubMail.zip`; Chrome uniquifies repeats). Every ZIP has one top folder, the ZIP name without `.zip`: `downloadZip` derives it and sends it as `root` with `build-zip`; `buildZip` writes entries, reports, `missing.txt` and `log.txt` below it (entry names in the requests stay relative). Without it, macOS Archive Utility extracts a single-folder ZIP (ClubMail-only) without a wrapper folder, but a multi-folder ZIP into `<zip name>/`. E2E `zipEntries`/`zipText` assert the top folder and work with relative names. Open and close calls run through one promise queue (`offscreenQueue`), so double clicks and a close racing a new job can't collide.
- Click dispatch is URL-based, in this order: `clubMailConversationIds(tab.url)` matches `/clubmail/conversation/conversation-wrapper-personal-<a>-<b>/` and takes the ClubMail-only path; `profileUserId(tab.url)` matches profile, `/profile/fotos/…` and `/profile/fotoalbum/…` URLs and takes the album path even with a lightbox open; every other URL takes the lightbox path.
- ClubMail-only path: `fetchClubMailImages([a, b])` alone (via `extractAllWithProgress`, API phase 0 → 10 %), then `toClubMailZipRequest(raw, date)` → `<Partner>_ClubMail.zip` with only the `ClubMail/` folder. The partner name comes from the first message of `raw.partnerId`. A failure throws `ClubMailApiError` with the fetcher's `reason` as `.reason` (red badge "ClubMail unavailable (<reason>)", built with `withReason`), no messages `NothingToDownloadError`. A conversation without attachments has `entries: []`; `buildZip` then zips the reports alone (it returns no blob only when entries exist but none loaded, or when there are neither entries nor reports).
- Album path: `fetchProfileAlbums(userId)` is injected with `executeScript({ func, args: [userId] })` and makes all API calls inside the tab, with the user's session. The service worker makes none. Steps: `GET /webauth/access_token` (`credentials: 'include'`) → `content.access_token`; then two POSTs to `https://apiv2.joyclub.com/graph/` with `Bearer` token: `getProfileAlbumList` (main album ids, regular albums, restricted ones with `imageCount` and `restrictionReason` only; `skippedReport` writes the raw reason, the enum values are `INSUFFICIENT_MEMBERSHIP`, `NEEDS_PERMISSION_BY_OWNER`, `NEEDS_VERIFICATION`, taken from JoyClub's frontend bundle since introspection is off) and `getProfileAlbumImageSources` (`sourceListJson` per id; `largestJpegUrl` picks the widest jpeg). It returns `{ failed: true }` instead of throwing; `toAlbumZipRequest` maps that to `AlbumApiError`.
- Photo fetches in `buildZip` (`lib/zip.js`): `fetchBytes` retries network errors, timeouts, HTTP 429 and 5xx twice (after 1 s, 2 s); other 4xx fail at once and go to `missing.txt`. `buildZip` takes an injectable `delay`, so unit tests pass a no-op instead of waiting.
- ZIP progress: `background.js` gives each ZIP job a `jobId`, sends it with `build-zip` and maps it to the tab in `zipJobTabs` until the build answers. `offscreen.js` sends `{ target: 'background', action: 'zip-progress', jobId, done, total }` from `buildZip`'s `onProgress`, throttled to one per whole percent (`throttleProgress` in `lib/progress.js`); progress for an unknown `jobId` is dropped. The API phase (0–10 %, resolved fetchers / fetcher count) is set by the service worker itself. The `onMessage` listener stays sync, since a returned promise would count as an async answer.
- E2E reads the badge sequence by wrapping `chrome.action.setBadgeText` inside the service worker (`recordBadgeTexts`); the last progress message may legitimately arrive after the build answer and be dropped, so assert containment, not the full sequence.
- Profile videos (`lib/video.js`, `lib/hls.js`, `.agents/changes/2026-10-09-missing-features/research-09-profile-videos.md`): `fetchProfileVideos(userId)` is the third fetcher of the album path (API phase 0 → 3 → 6 → 10 %, fallback `{ failed: true, reason: 'extension could not run on the page' }`). It POSTs `/video/lightbox/list` and `/video/lightbox/data` (form `cache_killer` + `data`, `media_source: 4`), reads `video_source` (HLS master `https://uservideo.joyclub.de/<guid>/hls/<id>.m3u8`) and `data-cookie-config` from each `media_html` attribute by regex (no DOM, so Node tests run it), then GETs `/aws/aws_signed_cookies` per video and turns the three `CloudFront-*` values into a signed-URL query (`Policy`, `Signature`, `Key-Pair-Id`; CloudFront accepts them as query, verified live; each is valid ~20 min and for its own `<guid>/hls/*` only). It never calls `/aws/track/watch` (counts a view). A locked FSK18 session gets no `data-video` (`{ id, locked: true }`); no bypass. `toVideoEntries` → `Videos/<Owner>_Videos_<nn>_<id>.mp4` entries `{ url: master, videoId, hls: { query } }` (numbered by list position, gaps for videos without source) and `skipped.txt` lines; `toAlbumZipRequest(raw, date, clubMail, videos)` reserves `Videos` like `ClubMail` and puts video entries between albums and ClubMail. In `buildZip`, video entries are fetched first (their parameters expire after ~20 min), the ZIP keeps the entry order. An entry with `hls` goes to `fetchVideo`: master → `bestVariant` (highest `BANDWIDTH`, then pixels; not position) → media playlist → segments one after the other, every URL via `fetchBytes` (same retries, label `video`, `credentials: 'omit'`) with the query appended; a 403 fetches fresh parameters from `hls.signing` (`<origin>/aws/aws_signed_cookies?mode&payload`, built by the fetcher, fetched by the offscreen document with the session cookies; `signedQueryOf` in `lib/video.js`, duplicated in the self-contained fetcher), retries that request once and keeps the fresh query (`video: re-signed` log line). `parseMediaPlaylist` → `{ segments: [{ url, range? }], map, encrypted }`: `EXT-X-BYTERANGE` parts are fetched with a `Range` header (a 200 with the whole file is sliced); `EXT-X-MAP` with an mp4 init section (fMP4/CMAF) → `joinFragments` (no mux.js), a TS init section is prepended to the TS parts; `remuxToMp4` (mux.js `Transmuxer`, all segments pushed, one flush) → fragmented mp4 (`ftyp`, `moov`, `moof`/`mdat`); it zeroes the version-0 durations of `mvhd`/`tkhd`/`mdhd`, which mux.js sets to `0xFFFFFFFF` (AVFoundation then showed 25–50 h), and numbers the `moof` boxes 1, 2, … (`mfhd`): mux.js writes 0 into every one, and AVFoundation (QuickTime) then reads only the first fragment, i.e. sound without picture. ffprobe, ffmpeg, Chrome and VLC ignore both, so check QuickTime compatibility with AVFoundation (`AVAssetReader` per track: frame count, last timestamp), not ffprobe. `EXT-X-KEY` (not `METHOD=NONE`) → `unsupported` (neither added nor missing; `buildZip` appends `Videos: <n> not supported (encrypted)` to `skipped.txt`); it is recorded as saved, since a retry would leave a ZIP of nothing (red badge) on every later click. A mux.js exception makes only that video missing (`remux failed`). `fetchProfileVideos` gives a video a query only when all three CloudFront values came back. Logs and `missing.txt` carry the URL without the signed query. Records hold `videos` (ids) only when there are any. A failed video fetcher sets `videosFailed`/`videosReason` on the request (like ClubMail): amber badge "videos unavailable (<reason>)" (`fetcherWarnings` in `background.js`), `warning` for `log.txt`, the log download on "nothing new". Badge texts count files, not photos ("n of m files", "n of m files missing"). `vendor/mux.min.js` (classic script, global `muxjs`, loaded by `offscreen.html`) is pinned like JSZip (`tests/unit/vendor-muxjs.test.js`). Host permission `https://uservideo.joyclub.de/*`. Fixture: `tests/fixtures/video/` (2 s ffmpeg `testsrc` + `sine`, two TS segments; `fmp4/` the same as fMP4 HLS, `-hls_segment_type fmp4 -hls_fmp4_init_filename init.mp4`; `byterange/` as one TS file, `-hls_flags single_file`) and `tests/fixtures/video-api.js`; regenerate with `ffmpeg -f lavfi -i testsrc=size=64x64:rate=10 -f lavfi -i sine=frequency=440:sample_rate=22050 -t 2 -pix_fmt yuv420p -c:v libx264 -profile:v baseline -g 10 -c:a aac -b:a 32k -f hls -hls_time 1 -hls_playlist_type vod -hls_segment_filename 'seg_%d.ts' media.m3u8`.

- ClubMail path: `handleActionClick` injects `fetchClubMailImages([userId])` (`lib/clubmail.js`) in parallel with `fetchProfileAlbums` (`extractAllWithProgress`, API phase 0 → 5 → 10 %). It takes the user ids from the URL (one from a profile, two from a conversation) and drops the own id; one partner id left → `{ origin, partnerId, messages }`, none (own profile) → `{ origin, messages: [] }` without a request, two (not the user's conversation) → `{ failed: true, reason: 'not your conversation' }`. Every failure carries a `reason` (`no session` (checked first: without the own id both ids stay partners), `not your conversation`, `HTTP <status>`, `bad response`, `timeout`, `network error`); errors are classified by `error.name`, not `instanceof`, since the function is serialised. Entry URLs are absolute `<origin>/clubmailv3/attachment/download/?attachment_id&conversation_sample_id&message_id` URLs (use each message's `conversation_sample_id`, it can differ from the wrapper ID); the offscreen document fetches them with `credentials: 'include'` (host permission exists). `messages` (author, time, raw `content`, reply, attachment file) feed `renderConversationMarkdown` and `renderConversationHtml` (`lib/transcript.js`), which `toAlbumZipRequest` puts into `reports` as `ClubMail/conversation.md` and `ClubMail/conversation.html` when there are messages. `content` is HTML; `lib/clubmail-content.js` converts it without a DOM (allowlist: `<br>`, smiley `alt`, http(s) `<a>` and `<j-a>` (album notices), entities; other tags stripped). After one fetcher rejects, `extractAllWithProgress` stops painting progress, so a late fetcher can't cover the red error badge.
- Failure log (`lib/log.js`): `handleActionClick` creates one `createLog()` per click and adds a line per step (`path: …`, `albums: …`, `clubmail: …`, `probe`, `zip: <n> added, <m> missing` or `zip: build failed`, `download started`, `error: <name>`; unexpected errors log only their name, since their message may hold page data), each with the ms since the click and optional `entry` (ZIP entry name), `status`, `reason`, `url` (query and fragment stripped by `stripQuery`). Never pass tokens, cookies or message text. `buildZip` keeps its own log (`photo: retry` per retried attempt, `photo: missing` per given-up photo, each with `entry`, since ClubMail attachment URLs differ only in the stripped query, and `status` or the error name as `reason`) on the click's `startedAt` and answers it as `logLines`; `buildZipOffscreen` sends a copy of the click log (`log: { startedAt, lines }`) and `warning` (= `clubMailFailed`) with `build-zip` and appends `logLines` to the click log, so a red build failure's log holds them too. `buildZip` writes `<top folder>/log.txt` (click log plus `logLines`, `renderLog`) when photos are missing or `warning` is set, i.e. exactly on an amber badge; it ends before the `zip: …` line. Clean clicks download nothing. Chrome hides `tab.url` on hosts without permission, so the log of a non-JoyClub click has no URL. Integration tests separate the log from content downloads with `logDownloads()`/`contentDownloads()`; E2E finds it with `chrome.downloads.search({ urlRegex: '^data:text/plain' })`.

## Testing
- Every change needs appropriate test coverage — write tests as soon as the functionality is coded, not at the end.
- All tests must pass before committing.
- Always set reasonable timeouts on operations that might hang.
- Follow the **test automation pyramid** (Martin Fowler): test at the lowest layer that meaningfully covers the functionality — do not duplicate coverage at a higher layer.
  - **Unit tests** (Node.js, no browser): pure functions. Run with `npm test`.
  - **Integration tests** (Node.js, external calls mocked): only for behavior that cannot be verified at unit level. Live in `tests/integration/`; stub `globalThis.chrome` before dynamically importing `background.js`. Run with `npm test`.
  - **E2E tests** (Playwright, Chrome with extension loaded): popup UI, extension lifecycle, and flows that require a real browser context. Run with `npm run test:e2e`. Uses `headless: false` — Chrome extensions require it; use headless mode for everything else. Apply the **Automation in Testing** pattern: automate setup and result verification; let the human perform only steps that need a real website. Document every remaining manual step and why it cannot be automated.
  - **Visual debugging**: when automated assertions are insufficient to diagnose a failure, take a whole-browser screenshot via macOS `screencapture` (e.g. `screencapture -x /tmp/debug.png`) or via Playwright's `page.screenshot()`, then analyse the image.
- Automate every testing step that can be automated.
- `npm test` runs lint + unit/integration tests. `npm run test:e2e` runs Playwright E2E tests. Both must pass before committing.
- E2E fixture (`tests/e2e/fixtures.js`): persistent Chromium context with the extension loaded, plus a local HTTP server for the image. JoyClub URLs are served from sanitised HTML in `tests/e2e/fixtures/` via `page.route`. Playwright cannot click the toolbar icon, so tests call `globalThis.handleActionClick(tab)` inside the service worker.
- E2E album API: `routeJoyclubApi` in `fixtures.js` routes the token endpoint and GraphQL (answered per `operationName`; `captions`/`profileText` default to `null`) via `context.route`, which also catches the fetches of the injected fetcher. GraphQL is cross-origin with an `authorization` header, so the route answers the `OPTIONS` preflight (`Access-Control-Allow-Headers`/`-Methods`) and sends the fixed `Access-Control-Allow-Origin: https://www.joyclub.de` on every GraphQL answer. The token route is same-origin and needs no CORS headers.
- E2E videos: `routeJoyclubApi({ videos })` routes the list, data and signed-values endpoints (always, an empty list by default, so every profile test gets no videos). The `joyclubServer` also answers for `uservideo.joyclub.de` (second `--host-resolver-rules` mapping, branch on the `Host` header) with the playlists and fixture segments, and 403 without the signed query.
- E2E ClubMail: `routeJoyclubApi` routes the message list (same-origin, no CORS). The conversation page is `tests/e2e/fixtures/conversation.html`. `context.route` does not reach the offscreen document (a hidden `background_page` target), so its attachment fetches go to a local HTTPS server (`joyclubServer` fixture, self-signed cert generated with `openssl` per run): Chrome runs with `--host-resolver-rules=MAP www.joyclub.de 127.0.0.1:<port>` and `--ignore-certificate-errors`. Tab requests are still caught by the routes first. Fixture data is synthetic (`tests/fixtures/clubmail-api.js`).
- Playwright saves downloads under GUID names, so E2E can assert only the filename the extension requested, not the name on disk. The real on-disk name is a manual check.
- The E2E browser runs with `--disable-features=LocalNetworkAccessChecks`: otherwise Chrome shows a permission prompt when the routed `https://www.joyclub.de` page loads its image from `127.0.0.1`, and `page.goto` hangs.
- Manual and live checks: do them yourself with `playwright-cli` and the user's cookies, never leave them to the user. The user exports the cookies to `~/Downloads` (`www.joyclub.de.cookies.json`, `identity.joyclub.com.cookies.json`); ask for a fresh export when they are missing or expired. Only steps that truly need a human stay `(manual testing required)`.
- Live check against a real session: `playwright-cli open --headed --config=<file>` with `browser.browserName: 'chromium'`, `browser.launchOptions` `{ channel: 'chromium', args: ['--disable-extensions-except=<repo>', '--load-extension=<repo>'] }` and a `userDataDir` (without `browserName` playwright-cli launches the managed Google Chrome, which ignores `--load-extension`: no service worker); add the user's cookies with `run-code` → `context.addCookies` (inline the JSON, `require` is unavailable; normalise `sameSite`). Click via `context.serviceWorkers()[0].evaluate(… handleActionClick(tab))`. Opening a conversation in the UI calls `read_conversation` itself, so abort that route to keep a conversation unread. Keep downloads and screenshots in the scratchpad, never in the repo. After a code change use a fresh `userDataDir`: a persistent profile keeps the old service worker modules.
